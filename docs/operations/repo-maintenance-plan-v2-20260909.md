### 0.2 조사 기준과 불확실성

이 문서는 **이전 대화에서 조사한 운영 계획과 유지보수 보완 7개 항목을 통합한 문서**다. 이번 통합 작업에서 원격 저장소를 새로 조회하거나 테스트를 재실행하지 않았다. 기존 계획 파일을 읽고 이 최종 계획 파일을 작성했으며, 저장소 파일은 변경하지 않았다.

초기 조사에서 확인한 공개 `dev` 기준 SHA는 `38feb9589dd7517fb44d3d260fcc56b7be8e765a`다. 공개 페이지를 읽은 조사이지, 전체 checkout을 고정해 실행한 감사가 아니다. 당시 확인한 Actions 실행 한 건은 성공·2분 5초였으며, 이것을 현재 전체 CI의 성능이나 Codex 리뷰 지연 실측으로 확대하지 않는다. [S01][S02]

브랜치 보호, required checks, Codex 실제 자동 호출 조건, Vercel/registry 계정 설정, 대기 시간·비용, 백엔드 설치 버전은 **착수 전 P00에서 다시 확인할 항목**이다. 아래 경로·명령은 초기 조사 및 보완 검토의 기준점이며, 이미 변경됐거나 기능이 존재하면 새로 만들지 않고 차이를 확인한다. 문서에 적힌 수치와 운영 주기는 별도 표시가 없는 한 **초기 제안값**이지 Codex 공식 제한이나 현재 강제 규칙이 아니다.

### 0.3 유지할 결정과 제외 범위

- `bot/*` 또는 `feat/*` → `dev` → 릴리스 PR → `main` 구조를 유지한다. `dev → main`은 merge, 작은 기능 PR은 squash를 기본으로 한다. 개인 작업은 세션별 worktree로 격리한다. [S03]
- 결정론 분석과 모델 기반 재작성의 경계를 유지한다. 분석 계층은 모델 계층에 의존하지 않는다. [S04]
- 제품의 `SKILL.md`·`agents/`와 저장소 개발용 `AGENTS.md`를 구분한다. 최근 기본 스킬 경로는 검증된 CLI 실행으로 바뀌었으므로 과거의 호스트 에이전트 직접 재작성 전제를 개발 규칙에 다시 넣지 않는다. [S05]
- 취소된 인간 평가 연구와 인간 라벨 SNS 코퍼스 과제는 재개하지 않는다. PR #778은 이를 명시적으로 `not_planned` 처리했고, 재개에 새 요청을 요구한다. 기존 증거와 의미 보존 안전장치를 없애라는 뜻은 아니다. [S06]
- 이 운영 개선에 임계값·가중치·윤문 프롬프트 변경이나 기존 연구 재평가를 섞지 않는다. 기존 npm 발행 보류도 자동으로 해제하지 않는다. 채널별 공개 상태는 별도로 확인하고 기록한다. [S07]

개발 구조를 정리한다는 이유로 전면 TypeScript·monorepo 전환, 전체 디렉터리 이동, 새로운 범용 QA 플랫폼을 선행하지 않는다. 운영 계획의 승인과 공개 Issue/PR 발행·merge·배포 권한은 별개다. 이 요청은 계획 작성이며, 실제 실행 단계의 외부 쓰기는 따로 승인받는다.

정책 문서와 실행 설정이 다른 값을 갖지 않도록 JSON 필드의 의미만 문서화하고, 표가 필요하면 설정에서 생성한다. 정책 변경은 독립 PR로 다루고, 해당 PR의 검사 강도를 그 PR 자체의 완화된 정책으로 낮추지 않는다.

현재 blanket ignore를 제거하는 대신, 승인한 루트 및 필요한 scoped AGENTS 파일만 명시적으로 허용하는 방식도 가능하다. `.omo/`, `.omc/`, `.insane-review/`, 원문·토큰·개인 프로필은 계속 비공개로 둔다. `CLAUDE.md`는 실제 사용이 필요한 경우에만 짧은 어댑터를 추가한다. 기존 private-asset 검사기도 이 공개/비공개 구분과 일치하는지 확인한다. scoped AGENTS가 `src/` 등의 npm 포함 경로 아래에 생기더라도 개발 전용 지침이 제품 패키지에 불필요하게 포함되지 않도록 pack 목록을 검사한다. 검사기를 통째로 완화하지 않는다.

### 2.2 루트 AGENTS의 최소 내용

처음에는 약 80~120줄 이내를 목표로 하고, 작업 에이전트의 권한과 코드 리뷰 규칙을 구분한다.

```md
# Repository work
- 시작 시 git 상태, 현재 브랜치, 적용되는 scoped 규칙을 확인한다.
- 요청받은 범위와 승인된 Issue의 acceptance criteria만 구현한다.
- 작업 브랜치는 최신 dev에서 만든다. 저장소 기본 브랜치 설정은 바꾸지 않는다.
- 다른 세션의 변경을 reset, stash, overwrite 또는 force-push하지 않는다.
- worktree 밖의 설정·인증·출력 경로·포트도 공유 여부를 확인한다.
- 제품 동작 변경에는 실패를 재현하는 동작 테스트와 계약 변경 여부를 함께 남긴다.
- 기대값 갱신만으로 결함을 숨기거나 핵심 테스트를 임의로 skip하지 않는다.
- 미실행·실패·취소·검증 완료를 구분하여 보고한다.
- 별도 권한 없이 공개 발행, 운영 배포, 계정 설정 변경을 하지 않는다.
- PR/Issue 및 릴리스 절차는 docs/WORKFLOW.md를 따른다.

## Code Review Rules
- 결정론 분석에서 모델·네트워크 실행 계층으로 새 의존성이 생기면 지적한다.
- 의미 보존 검증의 우회, 원문 오염, 숫자·부정·인과 관계의 비의도적 변경을 지적한다.
- 검증되지 않은 결과를 accepted로 표시하거나 private 원문·인증 정보가
  로그, telemetry, 공개 산출물에 노출되는 경로를 지적한다.
```

OpenAI 공식 문서는 루트와 변경 경로에 가까운 `AGENTS.md`의 `## Code Review Rules`를 적용하며, 핵심 규칙 2~3개부터 시작하고 lint 같은 기계적 검사는 CI에 두라고 안내한다. 별도 규칙을 추가한다면 `src/features/`, `api/`, `playground/`처럼 실제 경계별로 최소한만 둔다. [S22]

### 2.3 SSOT는 한 파일에 모든 것을 넣는 것이 아니다

| 대상 | 제안하는 소유권 | 검증 방식 |
|---|---|---|
| 소스 릴리스 버전 | 루트 `package.json` | 기존 `release:check`를 유지·확장하고 버전 mirror만 생성/동기화 |
| 배포 채널별 실제 상태 | registry/deployment 증거 + SHA·버전 manifest | source, web, npm root, npm alias 상태를 각각 기록 |
| 기본 설정 | `.patina.default.yaml`과 설정 로더의 명시적 계약 | 기본값·우선순위·배열/키 부재 처리의 동작 테스트 |
| 패턴·lexicon | 기존 원본 자료 | ID·개수·카탈로그 등 파생 값은 생성 또는 drift 검증 |
| 점수·보존 계약 | 실제 실행 상수/판정 경로와 `core/scoring.md`의 관계를 명시 | 점수 재설계 없이 기존 출력 snapshot 및 CLI/web 일치 검증 |
| 아키텍처 | 기존 ARCHITECTURE | 실제 import 경계 검사. 중복 설명보다 금지된 역방향 의존성을 검사 |
| 개발 프로세스 | WORKFLOW | 템플릿과 정책 검사기가 같은 필드를 사용 |
| 공개 계약 | ARCHITECTURE의 지원 경계와 해당 계약 테스트 | CLI/API/설정/설치의 지원·변경·폐기 여부 검증 |
| 백엔드 검증 상태 | 기존 backend 문서 또는 한 개의 버전 검증 기록 | 실제 버전·필수 기능·증거·검증일 연결. 지원 범위와 관측 사실 구분 |
| 공개 연구 결과 | 기존 증거 manifest와 생성 절차 | 역사적 결과 보존, private 원문 비공개, 운영 변경으로 재baseline 금지 |

버전 정책은 **기능 PR: 변경 설명과 semver 영향 기록 → 릴리스 준비: 한 번만 버전 확정·mirror 갱신**으로 통일한다. 현재 CONTRIBUTING의 기능별 버전 갱신 요구와 WORKFLOW의 릴리스 갱신 절차가 충돌하지 않도록 함께 고친다. [S10][S03]

처음부터 모든 문서를 생성기로 바꾸지 않는다. 버전 mirror 한 종류를 pilot으로 삼고, 이미 있는 checker/generator를 조사해 확장한다. 기존 문서 설명이나 다국어 예시를 전부 기계 생성 대상으로 간주하지 않는다.

### 2.4 정책·문서의 수명

문서는 성격에 따라 `current`, `proposal/experimental`, `retired`, `historical`을 구분한다. 기존 metadata 형식이 있으면 그것을 재사용하고, 문서마다 새 형식을 강제하지 않는다. 현재 규칙에는 소유 영역·최종 검증 기준을, 폐기 문서에는 대체 문서와 폐기 이유를, 역사적 결과에는 당시 SHA·조건을 남긴다.

역사적 벤치마크·연구 결론은 현재 버전 수치로 자동 덮어쓰지 않는다. 이미 취소한 연구나 제거한 기능을 오래된 문서 하나 때문에 재개하지 않는다. `check-retired-concepts`처럼 기존 검사가 담당할 수 있는 영역을 먼저 확장한다. [S06][S16]

새로운 ADR 저장소나 유지보수 문서를 일괄 생성하지 않는다. 중요한 호환성·의존성 방향·상태 수명 결정은 기존 문서의 짧은 결정 기록 또는 연결 Issue에 이유·대안·대체 관계를 남긴다. 사람이 읽는 정책과 기계 설정에 같은 수치를 따로 유지하지 않는다. 기계 설정을 도입한 시점부터 해당 필드의 정본은 그 설정이다.

## 3. 저장소 구조: 이동보다 경계부터

현재 위치는 우선 유지하고 역할을 다음처럼 명시한다. 이 표는 이사 계획이 아니라 책임 지도다. [S04][S16]

```text
bin/                  설치·CLI·스킬 진입점
src/features/         결정론 분석 계층
src/의 나머지 영역    재작성 orchestration, provider, CLI 및 공용 기반
api/                  서버리스 HTTP 경계
playground/           브라우저 UI
core/, patterns/,
lexicon/, personas/,
document-types/       제품이 사용하는 규칙·지식 자산
SKILL.md, agents/      제품 스킬 및 제품 에이전트 계약
packages/
  patina-humanizer/    배포용 alias 패키지
scripts/              생성·검증·연구·발행 도구
services/             별도 운영 서비스 경계
tests/                현재 unit/e2e/quality 구조 유지
```

공유 기반 계층의 허용 import를 먼저 분류한 뒤, 새로 추가되는 역방향 의존성을 막는다. `features → model/network`, 브라우저→서버 비밀 설정, 런타임→개인 연구 스크립트 같은 경계를 우선한다. 기존 예외가 발견되면 사유와 제거 대상을 등록하고 신규 위반부터 막는다. 단순 문자열 검색만으로 실제 import graph를 검증했다고 표현하지 않는다.

파일 이동은 실제 중복 책임이나 순환 의존성이 확인됐을 때만 한다. **이동 PR과 동작 변경 PR은 분리**하며, import 경로·설치 스크립트·npm 포함 파일·CLI/웹 진입점의 호환성을 함께 검사한다. `apps/*`, 전체 monorepo, 전면 TypeScript 전환은 이번 선행 과제가 아니다.

타입 검사는 이미 있는 도구를 이용해 작은 모듈부터 `@ts-check` 또는 별도 checked-JS 설정으로 시작한다. 전체 `checkJs:true` 전환으로 수천 줄의 수정 PR을 만들지 않는다. 로컬 lint는 `.gitignore`와 별개이므로 개인 증거 폴더를 정확히 제외하되 실제 소스 오류를 숨기지 않는다. #781에는 `.omo/evidence`의 기존 lint 오류가 남았다는 기록이 있다. [S17][S01][S23]

### 3.1 리팩터링 착수 기준

파일 길이 하나로 분할하지 않는다. 최근 변경에서 **함께 자주 수정되는 파일, 반복 결함, 병합 충돌, 독립 테스트가 어려운 책임**을 먼저 찾는다. 예를 들어 하나의 정책 변경마다 CLI·웹·검증 세 곳의 같은 판단을 고쳐야 한다면, 도메인 정책 중복인지 표현 계층 차이인지 확인한다. 겉모양이 비슷한 코드라는 이유로 서로 다른 책임을 묶지 않는다.

리팩터링 Issue에는 관찰한 사례, 개선할 책임 경계, 바꾸지 않을 공개 계약, 검증·rollback을 적는다. 첫 pilot은 결함이나 반복 수정의 증거가 있는 경계 하나다. 이동·추출·동작 변경을 한 PR에 모두 묶지 않되, 중간 상태가 실행 불가능하거나 안전하지 않은 분할도 허용하지 않는다.

### 3.2 임시 코드·호환 분기의 제거 조건

임시 fallback·migration 분기·실험 플래그·장기 TODO에는 `도입 이유 / 소유 영역·담당자 / 제거 조건 / 검토 또는 목표 버전`을 연결한다. 새 전용 시스템보다 기존 Issue/주석/문서 중 하나를 정본으로 사용한다.

목표일이 됐다고 자동 삭제하지 않는다. 지원 중인 구버전 사용, rollback 경로, 데이터 변환의 비가역성, 외부 도구 복구 여부를 확인한 뒤 별도 작은 PR로 제거한다. 영구적인 안전 차단 기능은 임시 실험 플래그와 구분한다. 폐기 완료는 코드뿐 아니라 설정·문서·테스트·패키지 포함 경로까지 확인하되 역사적 증거를 지우지는 않는다.

**완료 기준:** 새 역방향 의존성이 검사에서 실패하고, 선택한 리팩터링은 기존 동작을 보존하며, 임시 분기는 존속 이유 또는 명시적인 제거 조건을 갖는다.

## 4. 공개 계약·호환성·지원 정책

버전 숫자 동기화와 사용자 동작의 호환성은 따로 관리한다. 초기 보완 검토는 구버전 설정에 대한 migration error와 내부 모듈의 지원 경계가 이미 문서화된 사례를 기준으로 삼았다. 현재 정책을 확인한 뒤 이를 연결하고, 내부 파일이 접근 가능하다는 이유만으로 전부 공개 API로 확정하지 않는다. [S04]

### 4.1 계약 목록과 대표 검증

| 경계 | 명시할 계약 | 대표 검증 |
|---|---|---|
| CLI | 지원 옵션·기본값·종료 코드·stdout/stderr·JSON 출력·입력/출력 파일 처리 | 기존 호출을 고정 입력으로 실행. 오류는 문서화한 종료 코드·채널로 반환 |
| API·스트리밍 | 필드·상태값·이벤트 순서·정상 완료/실패/취소·accepted/below-floor 구분 | 소비자 fixture가 응답을 해석. 잘린 스트림이나 실패를 정상 완료로 표시하지 않음 |
| 설정·사용자 자산 | 기본값·우선순위·스키마·잘못된 키·이전 Persona/설정의 처리 | 지원 구버전은 유지, 비지원 구버전은 안내된 오류/명시적 migration으로 처리 |
| 설치·패키지·스킬 | 진입점·alias·패키지 포함 자산·제품 SKILL 경로·내부 import 지원 범위 | tarball에서 실제 설치·실행. 개발용 private/agent 기록은 미포함 |
| 실행 환경 | Node 지원 범위·공표한 OS·필요 외부 CLI 기능 | 지원 조합의 대표 smoke. 최신 검증 버전과 최소 지원 정책을 구분 |

공개 계약의 정본은 ARCHITECTURE와 기존 사용자 문서의 명시적 연결, 실행 증거는 해당 계약 테스트다. 설명을 별도 계약 파일 여러 개로 복제하지 않는다.

### 4.2 계약 변경 PR의 필수 내용

경계를 건드리는 PR은 `호환 유지 / 의도적 변경 / 폐기` 중 하나와 semver 영향을 선언한다. 기존 입력·응답 소비자가 어떤 결과를 받는지, migration 또는 명시적 실패가 필요한지, rollback 시 이전 버전이 새 상태를 읽을 수 있는지 설명한다.

지원 구버전을 무조건 영구 유지하지 않는다. 대신 지원 범위 밖 입력을 조용히 잘못 해석하지 않도록 한다. 기존 JSON 필드/종료 코드/상태값 변경, 설정 기본값 변경, Node floor 인상, `exports` 제한 추가는 작은 diff라도 계약 검토 대상이다. 임계값·윤문 정책 변경을 이 호환성 정리 작업에 숨기지 않는다.

처음에는 CLI JSON/종료 코드와 설정 처리처럼 대표 경계 한두 개를 고정한다. 이후 관련 코드 변경 때 범위를 넓힌다. 동적 시간·ID·비결정적 모델 문장은 전체 문자열 snapshot으로 잠그지 말고 문서화한 필드·관계·상태 전이를 검사한다.

**완료 기준:** 지원하는 이전 호출·설정·응답 소비 방식이 계약대로 동작하며, 비지원 입력은 의도된 오류와 안내로 종료된다. 계약을 어기는 의도적 변형 fixture가 실패한다.

## 5. PR·Issue·merge 운영 규칙

### 5.1 Issue는 의사결정 단위, PR은 검증·롤백 단위

Issue가 필요한 작업은 사용자 동작·API/CLI 계약 변경, 보안/개인정보/결제/배포, 여러 PR이 필요한 개선, 설계 선택이 필요한 리팩터링이다. 하나의 Issue 아래 여러 PR이 올 수 있다.

오탈자, 작은 문서 정정, 기존 동작의 작은 테스트 보강처럼 한 PR로 끝나는 저위험 변경에는 Issue를 강제하지 않는다. 대신 PR에 생략 이유와 완료 기준을 쓴다. PR에서 발견한 동일 범위 결함은 그 PR에서 수정하고 매번 새 Issue를 만들지 않는다. 보안 취약점과 private 원문은 공개 Issue에 올리지 않는다.

기존 Issue form을 재사용하고 다음 정보만 공통으로 요구한다: 문제/근거, 기대 결과, 범위와 비목표, acceptance criteria, 위험/검증, 담당자, 필요한 경우 PR 분할안. 같은 증상·경로·에러로 열린 Issue와 PR을 먼저 검색한다. 검색하지 않은 자동 중복 발행은 금지한다.

에이전트에게 구현 요청을 줬다고 해서 모든 관련 아이디어의 Issue 발행 권한까지 준 것으로 해석하지 않는다. 승인된 범위의 Issue/PR 발행 권한을 구분한다. 초기에는 다음 작업만 열고 장기 후보는 하나의 tracking Issue에 둔다.

### 5.2 기본 PR 예산 — 조정 가능한 운영 기준

| 항목 | 초기 기준 |
|---|---|
| 주된 목적 | 사용자에게 설명 가능한 하나의 동작·계약·책임 변경 |
| 권장 변경량 | 검토 대상 추가+삭제 200~400줄 |
| 분할 검토선 | 600줄 초과 또는 검토 대상 파일 15개 초과 |
| 함께 둘 것 | 구현, 해당 동작의 회귀 테스트, 필요한 계약 문서 |
| 분리할 것 | 무관한 정리, 버전 일괄 bump, 다른 기능, 생성 산출물 정비 |
| 완료 조건 | 독립적으로 merge 가능하며 독립 revert 가능 |
| 작업 중 상한 | 작성자당 Ready PR 최대 2개를 초기값으로 사용 |
| 비싼 QA 동시 실행 | 초기 worker 1개, 동시에 PR 1개 |

기계 생성물·lockfile·순수 이동은 의미 검토 예산에서 별도로 표시할 수 있지만, 전체 diff 비용에서는 사라지지 않는다. raw 추가/삭제와 검토 대상 추가/삭제를 모두 기록한다. 제외는 승인된 generator와 재생성 증거가 있는 파일에만 적용한다. 프롬프트·패턴·손으로 쓴 예시·테스트 fixture는 Markdown/JSON이어도 검토 대상이다.

600줄/15파일 초과를 무조건 거절하는 것은 아니다. 일괄 마이그레이션·동일한 기계적 수정·릴리스 집계처럼 더 쪼개면 안전성이 나빠지는 경우에는 분할 불가 이유, 검증 방식, rollback, 오너 승인으로 예외를 허용한다. 에이전트가 붙인 `size-exception` 라벨 하나만으로 승인하지 않는다.

첫 10개 PR은 경고로 예산을 관찰하고 실제 리뷰 시간과 false alarm을 본 뒤 차단 여부를 결정한다. 이 숫자는 Codex의 공식 입력 한도가 아니다.

### 5.3 Ready 이후에 비용을 쓴다

```text
범위 합의 → 작업 브랜치/격리 worktree → Draft PR
→ 로컬 표적 테스트 + 저비용 CI
→ Ready + 예산/증거 충족
→ 필요한 Codex 리뷰 / 브라우저 QA
→ 동일 head와 최신 base의 필수 검증 확인
→ maintainer merge → 작업 브랜치 정리
```

Draft는 공동 작업과 진행 상태 공유에 사용한다. 작은 수정마다 Ready 상태에서 비싼 리뷰를 다시 호출하지 않는다. 이미 열린 PR의 수정은 같은 PR에 쌓고, 새로운 범위가 생기면 별도 Issue/PR로 분리한다. 자동 수정→재리뷰 루프는 초기 2회 후 오너가 범위를 재판단하도록 제한한다. timeout이나 인증 실패에 무한 재시도하지 않는다.

native Codex 자동 리뷰가 Draft/Ready/새 push에 실제로 어떻게 반응하는지 먼저 확인한다. 지원하지 않는 라벨 제어를 지원한다고 가정하지 않는다. ready+CI 기준을 맞출 수 없다면 모든 PR 자동 호출을 끄고 명시적 리뷰 요청 한 경로로 통일한다. GitHub Codex, 별도 Action, Desktop에서 같은 diff의 코드 리뷰를 중복 수행하지 않는다. [S22]

### 5.4 PR 템플릿 추가 필드

```md
## 목적 / 연결 Issue
Refs #...
Issue 생략 시 사유:

## 범위 / 비목표
사용자가 관찰하는 변경:
이번 PR에서 하지 않는 것:

## 계약 / 위험 / 크기
contract: compatible | intentional-change | retirement | not-applicable
영향받는 공개 계약과 구버전 처리:
risk: low | standard | high
raw diff / reviewable diff:
크기 예외 승인 근거(해당 시):

## 검증
head SHA / base SHA / tested merge SHA(해당 시):
실행한 명령과 결과:
미실행 항목과 이유:
UI·CLI 재현 절차 또는 artifact:
기대값 변경 이유·수정 전 실패 증거(해당 시):
취소·timeout 후 자원 정리 확인(해당 시):

## 릴리스 / 되돌리기
semver 영향과 이유:
롤백 방법:
```

PR 제목은 `fix(playground): ...`, `test(skill): ...`, `ci: ...`처럼 변경 책임을 드러내도록 한다. 높은 위험은 diff 크기가 작아도 낮아지지 않는다. `api` 인증·결제, 발행 권한, 보존 판정, 원문 파일 변경은 별도 오너 확인 대상으로 둔다.

### 5.5 Issue 종료와 릴리스 PR 예외

Patina는 기본 브랜치가 main, 기능 PR 목적지는 dev다. GitHub의 PR 본문 closing keyword는 기본 브랜치 대상으로만 적용되므로 `dev` PR에 `Closes #...`를 적는 것만으로 완료 관리를 하지 않는다. [S03][S24]

정책은 **기능 Issue: dev에 구현이 합쳐지고 AC가 충족되면 명시적 종료 / 사용자 제공 여부: 릴리스 기록에서 별도 추적**으로 통일한다. 초기에는 담당자가 닫고, 필요해지면 권한 있는 metadata-only 자동화가 최종 PR과 AC를 확인해 닫는다. 다중 PR 작업은 마지막 PR 전에는 종료하지 않는다. 취소는 completed가 아닌 not_planned로 구분한다.

`dev → main` 릴리스 PR은 이미 검토된 변경을 집계하므로 일반 PR의 크기 한도에서 예외로 둔다. 포함 PR 목록, SHA/검증 증거, 신규 릴리스 변경만 검토하고 최종 통합 트리는 다시 시험한다. 과거 기능 전체를 매번 같은 AI에게 재리뷰시키지 않는다. 충돌 해결이나 새로운 동작을 릴리스 PR에 몰래 추가하면 그 부분은 새 검토 대상이다.

### 5.6 병합 책임과 예외

작업 에이전트는 구현과 증거 제출을, 리뷰 에이전트는 finding을, 오너는 위험 예외·merge·외부 발행 승인을 맡는다. 솔로 운영에서 별도 두 명의 사람 승인을 일괄 의무화하지 않는다. 자동 리뷰의 결론은 필수 CI·SHA 일치·오너 결정의 대체물이 아니다.

최신 base에 대한 통합 검증 방식은 P00에서 실제 branch protection을 읽고 결정한다. strict up-to-date가 선택되면 관련 필수 검사가 그 통합 트리를 검증하도록 맞춘다. 우선 오너가 병합을 직렬화하고, merge queue는 실제 병합 경합이 확인될 때만 도입한다. 마지막 순간 base가 이동하면 기존 통합 검증을 새 base의 증거로 취급하지 않는다.

긴급 변경도 최소 계약·보안 검증·정확한 커밋·되돌리기를 생략하지 않는다. 생략 가능한 비필수 검사가 있다면 이유와 사후 보완 담당/기한을 기록한다. 에이전트 스스로 위험 등급을 낮추거나 예외 라벨을 붙여 안전장치를 해제할 수 없다.

## 6. 재현 가능한 개발 환경·병렬 작업

### 6.1 깨끗한 환경의 개발 계약

개인 전역 패키지·실서비스 로그인·개인 설정이 없는 clone에서 설치와 기본 결정론 검증이 가능해야 한다. 실제 `package.json` scripts와 lockfile을 읽어 기존 진입점을 우선 사용한다. 문서에 존재하지 않는 `verify` 같은 명령을 있다고 가정하지 않는다. 진입점 통합이 필요하면 기존 검증 명령을 호출하는 얇은 구성만 추가한다. [S16]

설치에는 지원하는 Node와 lockfile 기준 의존성을 사용하고, 설치 과정의 예상치 못한 파일 변경을 확인한다. 문서화한 `npm ci` 등 기존 절차로 unit/계약/고정 fixture 검증을 수행한다. 실제 외부 CLI·모델 호출은 별도 명시적 프로파일이며 기본 테스트의 숨은 선행 조건으로 두지 않는다.

로컬 환경에 의존하는 시간·locale·timezone·난수·경로를 식별하고 테스트에서 고정하거나 주입한다. 모델 출력의 비결정성까지 완전 재현된다고 주장하지 않는다. 새 도구 설치가 필요하면 일회성 개인 설정 대신 문서화된 dev dependency/환경 요구로 관리한다.

### 6.2 worktree 밖의 공유 자원

WORKFLOW의 세션별 worktree 정책을 유지한다. worktree는 일부 refs·기본 설정을 공유하므로 실행 환경 전체의 격리와 동일하지 않다. 공유 설정을 임의로 변경하지 않는다. [S03][S37]

각 작업은 worktree/브랜치와 함께 테스트용 홈·설정·캐시·임시/출력 경로·포트·자신이 시작한 프로세스를 식별한다. 실제 개인 홈을 복제하지 않고, 필요한 최소 fixture 설정만 전용 경로에 만든다. 기존 설정 주입 지점이 있으면 재사용한다. 인증 시험은 따로 승인된 테스트용 자격 증명으로만 수행한다.

**격리할 상태와 의도적으로 공유할 제한을 구분한다.** 세션별 홈을 만들었다고 서비스 전역 quota·rate limit·동시 실행 제한까지 우회해서는 안 된다. lock과 lease가 보호하는 범위를 먼저 확인한다. 종료 시 소유권을 확인한 임시 디렉터리·포트·프로세스만 정리하고, 넓은 `pkill`, 무차별 `git clean/reset`, 다른 세션의 stale 추정 삭제를 하지 않는다.

공통 파일(`package.json`, lockfile, 공용 설정, 핵심 orchestration)을 동시에 수정할 작업은 오너가 담당 세션과 통합 순서를 정한다. 새 중앙 락 서버부터 만들지 않고 작은 작업 예약과 최신 dev 재동기화 절차로 시작한다. 공유 파일 충돌이 예상되는 작업은 직렬화한다.

### 6.3 지원 OS의 대표 smoke

P00에서 공표한 OS·Node 지원 범위를 먼저 확인한다. 지원하지 않는 조합을 이 계획으로 새로 약속하지 않는다. 지원 OS별 설치·실행·한글/공백 포함 경로·취소·출력 파일 처리의 대표 smoke를 만든다. 최소 지원 Node 변경은 별도 호환성 PR이다.

주 OS/Node의 기본 결정론 검증은 유지하고, 다른 OS smoke는 설치/경로/프로세스 관련 PR 및 릴리스에서 우선 실행한다. 모든 OS×Node×백엔드 조합을 매 PR에 곱하지 않는다. 브라우저 회귀는 좁은 화면·포커스·IME 등 실제 지원 경계를 기준으로 선택한다.

**완료 기준:** 깨끗한 환경에서 기본 검증이 성공하고, 두 세션의 동시 실행에서도 테스트 설정·산출물·프로세스가 섞이지 않는다. 실패·취소 후 다음 세션이 정상 실행된다.

## 7. 테스트·QA·Codex 리뷰 계약

### 7.1 글에서 가져올 것과 가져오지 않을 것

참고 글의 유용한 부분은 한 번에 한 PR 선택, QA 전용 checkout, 변경에 맞는 실제 앱 조작, 스크린샷, 검증한 head의 증거, 중간에 head가 바뀌면 승인하지 않는 규칙이다. 모든 PR을 매시간 재검사하거나 모델 판단만으로 Approve→merge 하는 형태는 그대로 도입하지 않는다. [S25]

역할은 셋으로 나눈다.

| 역할 | 답할 질문 | 산출물 |
|---|---|---|
| 결정론 CI | 계약·테스트·형식 검사를 통과했는가? | 신뢰 가능한 check와 로그 |
| Codex 코드 리뷰 | diff에 구체적인 결함이나 위험 경계 위반이 있는가? | 파일/줄·재현 근거가 있는 finding |
| 브라우저/실행 QA | 사용자가 실제 경로를 실행하면 기대 동작을 하는가? | 실행 환경·시나리오·증거·커밋 |

### 7.2 Patina의 첫 QA 시나리오

처음부터 범용 UI 에이전트 테스트 플랫폼을 만들지 않는다. #781에서 확인된 회귀를 기준으로 다음 경로부터 고정한다. 기존 테스트가 이미 담당하는 부분은 중복 작성하지 않고 실제 브라우저에서만 확인할 경계를 보강한다. [S01]

- 결과 복사와 복사 표시의 초기화, 행별 상태, 연속 클릭 시 타이머 간섭.
- 설정 영역의 Escape·바깥 클릭, 첫 입력 포커스와 기존 IME 동작 보존.
- Free/BYOK/Pro 진입점과 좁은 화면에서의 접근성.
- 재작성 진행 중, accepted, below-floor, 중단, 전송 실패의 구분과 복사 가능 여부.

UI 회귀는 고정 fixture/mock transport로 재현한다. 새 네트워크 모델 호출 없이도 상태 전이와 UI 동작을 검사할 수 있어야 한다. 실제 모델 호출은 provider/재작성/보존 관련 변경을 위한 별도 승인·예산의 검증으로 둔다. UI mock 통과를 실모델 윤문 품질 통과라고 보고하지 않는다.

### 7.3 QA 실행 계약

대상은 Draft가 아니고, 충돌이 없고, 필요한 선행 CI가 성공했고, 해당 QA 프로파일이 필요한 PR이다. 에이전트가 임의로 붙인 라벨만으로 private 인증을 사용할 권한을 얻지는 않는다.

1. 저장소·PR 번호·base/head SHA·QA 프로파일 버전을 고정한다. 실제 시험한 merge/tree/build 식별자를 추가한다.
2. 신뢰된 실행기와 읽기 전용 기본 규칙을 사용해 전용 QA 환경에 checkout한다. 개발자 작업 폴더를 reset/clean하지 않는다.
3. diff와 AC에서 시나리오를 고르되, 해당 영역의 필수 회귀 경로를 생략하지 않는다.
4. 테스트용 origin/preview, 포트, 프로세스, 테스트 계정을 명시한다. 운영 앱·실결제·사용자 원문은 대상에서 제외한다.
5. 명령, 기대값/실제값, exit code, 필요한 스크린샷을 수집한다. 에이전트 설명만으로 테스트 성공을 만들어내지 않는다.
6. 결과 제출 직전 head/base를 다시 확인한다. 대상이 바뀌었다면 stale로 남기고 새 커밋을 승인하지 않는다.
7. 자신이 띄운 프로세스와 환경만 정리한다. 다른 세션을 종료하지 않는다.

결과 상태는 `passed`, `failed`, `inconclusive`, `stale`, `canceled`를 구분한다. 로그인 불가, 실행 불가, 예산 소진, 증거 누락을 passed로 바꾸지 않는다. Desktop QA는 초기에는 comment/증거 제출만 하고 자동 Approve·merge 권한을 부여하지 않는다. 이를 도입해도 별도 사람 두 명의 승인 같은 병목을 의무화하지 않고 저장소 오너가 merge를 결정한다.

중복 키는 저장소/PR/head/검토 diff/프로파일 버전을 기준으로 만들고 base·실행 트리·적용 정책 버전도 증거에 남긴다. base만 바뀌어 기존 코드 리뷰를 재사용할 때는 검토 diff와 관련 의존성이 변하지 않았음을 확인해야 한다. 이전 통합 테스트 결과를 새 base의 결과로 재사용하지 않는다.

Desktop 로컬 작업은 컴퓨터와 앱이 켜져 있어야 한다. 따라서 개인 PC의 스케줄 작업을 무조건적인 유일한 merge gate로 두지 않는다. 초기에는 worker 한 대만 사용하고 다중 컴퓨터 확장 전에는 공유 lease·만료·중복 제출 방지부터 검증한다. [S26]

### 7.4 실행기와 보고자의 권한 분리

PR 코드와 npm lifecycle은 신뢰된 코드라고 가정하지 않는다. 외부 PR의 실행 환경에 발행 토큰, 개인 로그인 세션 전체, 운영 비밀, repository write token을 넣지 않는다. 폐기 가능한 sandbox/VM·제한된 네트워크·테스트용 인증을 사용한다. secret이 필요한 고위험 검증은 명시적으로 승인된 경로에서만 수행한다.

보고자는 저장소와 PR, 실행 ID, SHA, 결과 schema, artifact 경로/크기를 확인한 뒤 최소 권한으로 댓글/check를 남긴다. artifact에 들어 있는 shell이나 Markdown 지시문을 실행하지 않는다. privileged `pull_request_target`/`workflow_run`에서 임의 PR checkout과 install을 실행하지 않는다. [S27]

스크린샷·실행 로그는 CI artifact 또는 검토 가능한 첨부로 보관하고 매번 repo에 커밋하지 않는다. 비밀·개인정보를 가린 뒤 공개한다. 원문이 필요한 실모델 실험 기록은 기존 private 정책을 지킨다.

### 7.5 테스트 자체의 유지보수

**기대값 보호.** 버그 수정은 가능한 한 수정 전 실패·수정 후 통과를 보여 준다. 새 테스트가 이전 커밋에 없으면 테스트 부분만 이전 구현에 적용하거나 통제된 결함 재현으로 증거를 남긴다. 구현과 golden/snapshot을 함께 바꿨다는 사실만으로 결함이 고쳐졌다고 보지 않는다. 의도적 계약 변경은 이전 기대값이 더 이상 유효하지 않은 이유를 적는다. 결정론 점수·의미 보존 fixture의 기대값을 이 운영 작업에서 임의로 재baseline하지 않는다.

**실제로 결함을 잡는지 확인.** 대표 회귀와 핵심 안전장치에는 잘못된 상태·숫자/부정/인과 변형·누락된 terminal event 등 제한된 negative fixture를 둔다. 무수정 원문 fallback을 정상 윤문 성공으로 표시하지 않는다. 전체 mutation testing 플랫폼을 선행하지 않는다. 모델 문장의 특정 문구 존재만 검사해 사용자 동작이나 품질을 검증한 것으로 표현하지 않는다.

**불안정한 테스트 관리.** 제품 결함, 테스트 환경 결함, 외부 서비스 장애를 구분한다. 초기 격리 검토 기한은 7일로 두고 담당자·추적 Issue·재현 증거·복구 조건을 기록한다. 임시 격리 중에도 별도 실행 결과를 남긴다. 의미 보존·인증·발행 안전장치의 필수 검사는 동등한 대체 검증과 오너 승인 없이 격리하지 않는다. 기한이 지나도 자동 연장하거나 조용히 삭제하지 않고 오너에게 다시 올린다.

재실행으로 첫 실패를 덮지 않는다. 명확한 일시적 인프라 실패에 제한된 재시도를 허용해도 최초 결과·사유·횟수를 남긴다. 최종 성공만 보고해 불안정성이 보이지 않게 만드는 흐름은 금지한다. 시간·네트워크에 기대는 임의 sleep 대신 통제 가능한 이벤트·clock·명시적 bounded wait를 우선한다.

### 7.6 취소·timeout·자원 정리

기존 cancellation 테스트와 백엔드 timeout/retry 계약을 확장한다. `AbortError`를 반환했다는 사실과 실제 작업이 정리됐다는 사실을 분리해 확인한다. 현재 코드의 결함을 미리 단정하지 말고, 다음 시나리오가 테스트되는지 먼저 확인한다. [S33][S34]

| 시나리오 | 검사할 완료 상태 |
|---|---|
| 실행 전 취소·작업 중 취소·timeout | 호출자에게 명확한 종료 상태. 해당 작업의 자식 프로세스와 필요한 경우 소유 프로세스 트리가 종료 |
| stdout/stderr 포화·부분 스트림·비정상 종료 | deadlock 없이 정해진 종료/오류로 정리. 수집 결과를 정상 완료로 승격하지 않음 |
| 동시 실행 슬롯·lease·임시 파일 | 자기 소유 자원만 해제. 다른 작업의 파일/슬롯을 손상하지 않음 |
| 직전 실행이 실패한 뒤 다음 호출 | 점유 상태나 포트 잔존 때문에 다음 호출이 막히지 않음 |

종료를 확인하는 테스트는 소유 PID·생성 토큰·heartbeat 등 지원 OS에 맞는 증거를 사용하고 단순 지연 후 추측으로 통과시키지 않는다. SIGTERM 미응답 후 강제 종료 같은 기존 종료 정책이 있다면 보존하고 시험한다. OS별 정책 차이는 명시한다. 실제 공유 서비스의 전역 제한을 무시하는 테스트 구성을 만들지 않는다.

**완료 기준:** 과거 회귀를 통제해 재현하면 테스트가 실패하고, 취소/timeout 이후 자원 정리와 다음 호출 성공이 모두 확인된다. 필요한 검사가 격리·미실행 상태이면 merge gate가 그 사실을 숨기지 않는다.

## 8. CI 개선·필수 검증의 신뢰성

### 8.1 먼저 할 것 — 현 검증을 줄이지 않고 낭비 제거

기존 test workflow에 PR별 `concurrency`와 이전 실행 취소, 명시적인 timeout, 최소 권한을 넣는다. 취소 그룹은 workflow와 PR/branch를 구분하고 PR 검사 취소가 릴리스 발행까지 중단시키지 않도록 한다.

초기 조사 기준으로 Node 24와 floating `lts/*` 중복을 없애고 lint/일반 CI 호스트를 24로 맞추는 안을 우선 검토한다. 착수 시 지원표와 실제 매트릭스를 다시 읽고 중복 여부를 확정한다. 기존 Node 18.1 최소 버전 smoke와 20/22 호환성 검사는 지원 정책을 바꾸기 전까지 남긴다. Node floor 인상이나 EOL 지원 종료는 별도 Issue/호환성 PR로 처리한다. [S14][S15][S16]

현재 전체 deterministic 테스트가 빠르므로 처음에는 주 Node에서 전체 suite를 유지한다. test sharding, 원격 build cache, 복잡한 동적 matrix는 도입하지 않는다. PR 검증과 merge 후 dev 통합 검증은 서로 다른 tree를 확인할 수 있으므로 단순히 중복이라고 삭제하지 않는다.

### 8.2 측정 후 할 것 — 경로 기반 검증

문서-only와 코드 PR의 runner 사용량 차이가 의미 있는 경우에만 프로파일 분기를 적용한다.

| 변경 종류 | 기본 검증 | 추가 검증 |
|---|---|---|
| 허용된 사용자 문서-only | 문서 링크/형식, private 자산 검사, 필요한 metadata | 관련 문서 생성 drift |
| 제품 Markdown: SKILL/core/patterns/lexicon 등 | 런타임 계약 및 관련 전체 결정론 검증 | 출력·의미 보존 fixture |
| CLI/설치/설정 | unit/e2e, 패키지·설정 계약 | 설치 실행/alias smoke |
| playground/UI | 공통 결정론 검증 + UI regression | 해당 경로의 브라우저 QA |
| API/인증/결제/보존 판정 | 보수적인 전체 검사 | 오너가 승인한 고위험 검증 |
| CI/보안 설정/package/lock/분류 불명 | 전체 검사 | 정책 회귀·공급망 검사 |

확장자만으로 분류하지 않는다. rename은 이전/새 경로를 모두 반영하고, API 파일 목록의 pagination/잘림·파싱 실패는 docs-only로 처리하지 않는다. 알 수 없는 변경은 전체 검증 또는 명시적인 실패로 닫는다.

필수 상태는 고정 이름 `ci/required` 하나로 집계한다. workflow 자체는 항상 시작하고, 집계기는 `always()`로 실행하여 **계획상 필요한 job이 실제 success인지** 확인한다. 필요한 job의 skipped, canceled, missing을 성공으로 취급하지 않는다. 변경 분류 계획이 없는 상태도 실패다. GitHub는 workflow 전체 skip과 job skip을 서로 다르게 처리하므로 경로 필터를 required workflow 최상단에 붙이지 않는다. [S28]

보호 규칙 전환은 새 check가 실제 PR에서 생성되는지 검증한 다음 한다. 기존 required check를 먼저 제거해 잠시 무검증 merge가 가능한 상태를 만들지 않는다. `dev/main` force-push·삭제 제한, 최신 base 통합 검증, 발행 권한은 설정을 읽어 확인한 뒤 적용한다. 새 사람이 여러 명 승인해야 하는 규칙이나 merge queue는 초기 필수 요건으로 두지 않는다.

### 8.3 변경 분류기·검사 정책 자체의 변경

정책 파일·workflow·검사기 변경은 고위험 검토 대상으로 다루고 신뢰된 base의 정책으로 먼저 평가한다. PR이 자신의 필수 검사 목록을 줄여 스스로 통과시키지 못하도록 한다. rename·파일 목록 pagination/잘림·삭제·알 수 없는 경로·누락된 실행 결과를 negative test에 포함한다.

체크 이름만 같다는 사실로 신뢰하지 않는다. 실제 check 발행 주체와 workflow identity를 P00에서 확인하고, 플랫폼에서 지원하는 범위에서 승인된 발행 경로를 사용한다. required gate 전환은 새 check의 정상/실패/skip/cancel 케이스를 먼저 증명한 뒤 오너가 보호 설정을 변경한다.

PR별 concurrency에는 workflow와 PR/branch 구분을 포함한다. 릴리스 발행·의도적인 정기 검증을 PR의 오래된 실행과 같은 취소 그룹에 넣지 않는다. 최초 실패 기록과 artifact가 재실행으로 사라지지 않도록 증거를 연결한다. 캐시 최적화가 필요해져도 신뢰 경계가 다른 실행의 산출물을 무검증 재사용하지 않는다.

## 9. 외부 CLI/API 호환성과 의존성 갱신

### 9.1 외부 도구 변경을 별도 위험으로 관리

백엔드가 늘어도 retry/fallback/timeout 책임을 새 공통 계층에 중복 추가하지 않는다. 기존 `src/backends/contract.js`의 소유권·전체 예산을 먼저 확인하고 동일 책임이 두 계층에서 증폭되지 않는지 시험한다. [S33]

기존 backend 문서나 한 개의 검증 기록에 `도구 식별자 / 실제 버전 / 필요한 기능·출력 형식 / 검증일 / 증거 / 상태`를 연결한다. 이는 최소 지원 버전 선언과 다른 정보다. 자격 증명·원문·사용자 경로를 기록하지 않는다.

| 상태 | 의미와 조치 |
|---|---|
| 검증됨 | 그 버전과 해당 시나리오에서 통과. 모든 기능·품질·미래 버전을 보장하지 않음 |
| 미검증 | 새 버전 또는 증거 없음. 단지 버전이 새롭다는 이유로 일괄 사용 금지하지 않음 |
| 호환성 문제 확인 | 필요한 기능/파싱/취소 등의 불일치가 재현됨. 문제 범위·회피책·지원 상태를 명시 |
| 실행 불가·외부 장애 | 설치/인증/quota/네트워크/서비스 장애. 제품 품질 점수나 호환성 통과로 변환하지 않음 |

필요한 능력이 실제로 없거나 응답을 안전하게 해석할 수 없으면 문서화한 오류나 기존 안전 fallback으로 처리한다. 알 수 없는 출력으로 accepted 성공을 만들어내지 않는다. 미검증 버전 경고 정책 자체가 사용자 동작을 바꾸면 별도의 호환성 검토를 받는다.

### 9.2 고정 fixture와 실제 호환성 점검의 분리

PR에서는 고정 fixture로 요청 구성·출력 파싱·오류·중단·시간 제한을 검사한다. fixture가 실제 외부 응답에서 유래했다면 도구 버전·채집 조건을 적고 비밀/원문을 제거한다. 기록만 녹화했다고 모든 에러 경계를 검증한 것으로 보지 않는다.

실제 도구 점검은 승인된 테스트 환경에서 백엔드 하나부터 시작한다. 실제 도구/모델 ID·버전·timeout·최대 호출 수·비용·인증 경로를 명시하고, 결과를 고정 fixture 통과와 구분한다. 단순 연결 점검을 윤문 품질 실험이나 취소된 연구 재개로 바꾸지 않는다.

일반 PR의 필수 CI는 외부 서비스 가용성에 종속시키지 않는다. 단, 백엔드 계약을 직접 바꾸는 PR에서 필요한 실제 검증이 실행 불가하면 inconclusive로 남기고 오너가 보류·대체 검증을 결정한다. 장애 상태를 성공 처리하지 않는다. 동일한 외부 장애는 하나의 추적 기록으로 합치고 자동 Issue를 반복 발행하지 않는다.

### 9.3 의존성 갱신 주기·PR 예산

사용 중인 의존성 업데이트 도구를 먼저 확인하고 없을 때만 하나를 선택한다. 초기 운영값은 **일반 업데이트 주 1회, 열린 일반 업데이트 PR 최대 2개**다. 관련된 개발 도구의 patch/minor는 한 책임 범위에서 묶고 major·런타임 계약 영향은 별도 PR로 처리한다. 묶음이 PR 예산이나 독립 rollback 조건을 깨면 다시 나눈다.

보안 업데이트는 정기 창을 기다리지 않고 노출 범위·영향·우회책을 우선 분류한다. 일반 업데이트 상한과 별도 관리하며 무조건 자동 merge하지 않는다. Dependabot을 사용한다면 일정·그룹·open PR 제한과 보안 업데이트의 별도 동작을 확인해 설정한다. [S36]

lockfile만 바뀌었다고 안전한 변경으로 간주하지 않는다. 실제 설치·관련 테스트·package smoke를 선택하고, 새로운 lifecycle이나 런타임 의존성의 목적을 확인한다. 외부 action은 승인된 출처·최소 권한을 검토하고, 가능하면 불변 참조를 사용해 갱신도 같은 절차로 검토한다. 기존 예외는 사유를 기록하고 새 예외부터 늘리지 않는다.

**완료 기준:** 외부 도구 출력 변경·인증 실패·quota·timeout이 구분돼 보고되고, 일반 의존성 PR이 리뷰 대기열을 무제한 점유하지 않는다. 동일 원인의 반복 장애는 하나의 기록으로 관리한다.

## 10. CD·검증 산출물·부분 실패 복구

초기 조사에서 확인한 release workflow의 main 도달 가능 커밋 검사, 기본 dry-run, release metadata/private asset 검사, npm 성공 후 GitHub Release 생성은 유지할 가치가 있다. GHCR도 이미 실행 검증한 이미지를 push하는 흐름을 갖고 있다. 개선은 이 안전장치를 없애는 작업이 아니다. [S18]

### 10.1 npm

```text
릴리스 대상 SHA/버전/채널 확정
→ 전체 릴리스 검증
→ root와 alias 실제 tarball 생성
→ tarball hash + 포함 파일 기록
→ 깨끗한 환경에 tarball 설치·CLI smoke
→ 승인된 채널만 동일 tarball 발행
→ registry 결과와 integrity 확인
→ 채널별 완료 기록 / GitHub Release
```

실제 `.tgz`를 smoke-test하고 그 파일을 발행한다. 루트와 alias 연결도 local registry 또는 검증 가능한 설치 구성에서 시험한다. 검증을 중복 수행하지 않게 lifecycle을 정리하되 `prepublishOnly`를 무조건 삭제하거나 모든 `--ignore-scripts`를 켜서 방어를 우회하지 않는다. npm은 tarball 발행과 registry integrity를 지원하므로 같은 파일을 기준으로 검증·발행을 연결할 수 있다. [S29]

부분 실패 정책을 정한다. root 성공 뒤 alias 실패 시 root를 재발행하려다 끝나지 않도록, 이미 존재하는 버전의 integrity가 기대 artifact와 같을 때만 완료된 단계로 인정한다. 다른 bytes면 중단한다. timeout 뒤 발행 여부가 불분명한 경우에도 registry 확인 없이 무조건 재시도하지 않는다. GitHub Release만 실패했으면 그 단계만 복구한다.

릴리스는 동시에 하나만 발행한다. 다른 릴리스 요청이 이전 발행을 취소하지 않게 하고, 동일 버전 재실행과 오래된 버전의 `latest` 승격을 막는다. source가 main에 포함됐다는 사실만으로 최신 배포 버전임을 보장한다고 취급하지 않는다. 과거 버전 발행이나 dist-tag 변경은 별도 승인 경로다.

초기 조사 당시 YAML은 `NPM_TOKEN`을 참조했다. OIDC trusted publishing 전환은 npm 패키지 설정과 workflow identity를 실제 확인한 후 진행한다. `id-token: write`와 `--provenance`가 있다는 것만으로 토큰 없는 발행이 이미 설정됐다고 단정하지 않는다. root/alias 각각의 설정을 확인하고 전환을 검증한 뒤 기존 token 경로를 정리한다. [S18][S30]

### 10.2 웹과 데이터 배포

Vercel 설정 파일은 build/배포 구성을 보여 주지만 계정 측 production branch·required checks·secret 범위를 증명하지 않는다. 이를 별도로 읽어 확인한다. 제안하는 계약은 **승인된 main SHA → 동일 SHA의 배포 → smoke → production 승격 → 즉시 rollback 가능한 이전 배포 식별자 보존**이다. 사용 중인 Vercel 기능에 맞게 실현하고, dashboard와 다른 두 번째 배포 경로를 만들지 않는다. [S31]

웹·소스·npm 버전이 의도적으로 다를 수 있으므로 일괄 숫자 동기화로 감추지 않는다. 채널별 `version`, `source_sha`, `artifact/deployment_id`, `status`, `hold_reason`을 기록한다. 발행 보류와 실패, 성공을 구분한다.

HF dataset workflow는 `main`을 checkout하는 수동 경로이므로, 별도 작은 후속 PR에서 dispatch 시점 SHA와 내보내기 artifact를 고정해 대기 중 main 이동으로 출처가 바뀌지 않도록 한다. 기존 production environment 보호는 유지한다. 취소된 연구를 재개하는 변경과 섞지 않는다. [S32]

### 10.3 발행과 rollback의 지원 계약

registry 업로드·GitHub Release·웹 승격은 명시적으로 승인된 채널만 수행한다. 필수 채널이 보류되거나 실패했는데 전체 발행 성공으로 표시하지 않는다. 발행이 없어도 tarball 생성·설치·모의 registry 상태 검증은 독립적으로 완료할 수 있어야 한다.

rollback은 이전 배포로 되돌리는 것뿐 아니라 이전 CLI/API가 현재 설정·저장 상태를 읽을 수 있는지도 확인한다. 비가역 변경이 있으면 사전 백업·명시적 migration 또는 roll-forward 절차를 정하고 별도 계약 변경으로 검토한다. 발행된 immutable 패키지를 덮어쓰는 방식으로 복구하지 않는다.

발행 workflow의 운영 권한·OIDC·token 변경은 dry-run 성공만으로 적용 완료라고 보지 않는다. 승인된 설정 경로에서 root/alias 및 실제 identity를 확인하고, 전환 후 불필요한 이전 자격 증명 경로를 정리한다. 의심되는 자격 증명 노출은 단순 rollback과 별개로 권한 있는 오너가 회수·교체 여부를 판단한다.

## 11. 제품 성능·자원 사용량의 회귀 예산

### 11.1 측정할 경계

기존 `benchmark:perf`와 관련 도구의 입력·측정 범위를 확인해 재사용한다. 별도 벤치마크 프레임워크를 선행하지 않는다. 다음은 추가 여부를 조사할 지표이며 현재 모두 측정된다는 뜻이 아니다. [S16]

| 지표 | 측정 계약 |
|---|---|
| CLI 시작 시간 | Node/OS·cold/warm·실행 명령을 고정. 설치 시간과 실행 시간을 분리 |
| 결정론 분석 | 공개 가능한 고정 입력의 크기·언어·해시, 반복 횟수, wall time 기록 |
| 메모리·패키지 크기 | 메모리 지표의 정의(RSS 등)와 측정 방식, 실제 npm tarball bytes를 명시 |
| 재작성 자원 | 전체 시도·재시도·fallback의 호출 수/시간/토큰, 완료·실패·취소·미실행 상태 구분 |

외부 서비스 지연·모델 변동을 로컬 분석 속도 회귀와 섞지 않는다. 호출 실패나 미실행을 0비용의 정상 성공으로 계산하지 않는다. 토큰/비용이 관측되지 않으면 unknown/null로 두고 추정이면 단가·조건을 표시한다.

### 11.2 경고에서 시작하는 예산

먼저 같은 환경의 반복 측정으로 변동 폭과 기준선을 만든다. 공유 runner에서 한 번 느려진 결과로 PR을 차단하지 않는다. 초기에는 경고·추세만 기록하고, 안정적인 지표에 한해 최소 표본·측정 조건·허용 편차·예외 승인 기준을 합의한 뒤 blocking 여부를 결정한다. 실측 전 절감률이나 정확한 p95를 약속하지 않는다.

기존 retry/timeout 계약의 상한·소유권을 먼저 테스트로 고정한다. 전체 요청 시간과 백엔드별 timeout을 구분하고, 재시도 계층 중복으로 전체 예산이 늘어나지 않는지 확인한다. 호출/시간 상한 자체를 바꾸는 것은 제품 동작 변경이므로 이 측정 작업과 분리한다. [S33]

성능 기록은 artifact 또는 기존 benchmark 이력으로 남기고 매 실행 장문 로그를 저장소에 커밋하지 않는다. 기준선 갱신에는 SHA·변경 이유·환경 차이를 남긴다. private 원문을 성능 fixture로 사용하지 않는다.

**완료 기준:** 설치 크기·시작 시간·호출 수 증가가 릴리스 전에 드러나며, 증가가 코드 변화인지 환경 노이즈인지 판단할 증거가 있다. 성능 향상을 위해 정확성·의미 보존 검증을 제거하지 않는다.

## 12. 관측 데이터·장애 대응·복구 검증

### 12.1 관측의 계산 계약

기존 집계형 관측 코드를 먼저 확인하고 새 수집 SDK부터 추가하지 않는다. 후속 보완 검토는 지연/토큰/호출의 구간 기록·보관 정책, Free/BYOK 성공 표본 수집을 주의점으로 제시했다. 정확한 이벤트/표본/보관 구현은 P00·P21a에서 재확인한다. [S35]

성공은 표본 수집하고 실패는 전수 수집하는 구조라면 raw event 수를 그대로 나눠 장애율로 표시하지 않는다. 각 지표의 분자·분모·표본 확률·집계 창·누락을 명시하고, 필요한 정보가 없으면 유효한 비율을 산출할 수 없다고 표시한다. 표본 확률을 안다는 이유만으로 편향 문제가 모두 해소됐다고 가정하지 않는다. 거친 지연 bucket은 구간 또는 근사치로 표시하고 정확한 p95로 주장하지 않는다.

사용자 취소, 인증/quota, provider 장애, 제품 오류, below-floor 결과를 의미에 맞게 구분한다. 진단 목적으로 accepted 기준을 느슨하게 하거나 오류를 숨기지 않는다. 성공·실패 정의가 바뀌면 지표 시계열의 변경 지점을 남긴다.

### 12.2 진단 가능성과 개인정보 경계

가능한 기존 채널/배포 정보로 운영 증거와 source SHA·배포 ID를 연결한다. 모든 요청에 새 고카디널리티 식별자를 무조건 추가하거나 원문 해시만 있으면 익명이라고 간주하지 않는다. 집계 데이터만으로 개인 요청을 복원할 수 있다고 주장하지 않는다.

원문·BYOK 키·토큰·개인 경로를 로그/스크린샷/Issue에 넣지 않는다. 기존 보관 시간과 접근 경계를 유지하고, 진단 수집 확대·보관 연장은 별도 개인정보 위험 검토를 받는다. 공유 가능한 최소 재현 fixture를 만들어 사용하고 private 원문을 공개 회귀 테스트로 복사하지 않는다.

### 12.3 짧은 장애 대응 절차

기존 운영 문서 한 곳에 다음 흐름을 둔다.

```text
이상 감지와 증거 확인
→ 영향 채널·배포·기능 및 오류 종류 구분
→ 오너에게 알림·중복 장애 통합
→ 승인된 기능 제한 / rollback / roll-forward 선택
→ 복구 smoke와 지표 정의에 맞는 정상화 확인
→ 원인·타임라인·최소 회귀 사례·후속 담당 기록
```

알림에는 확인할 지표·배포·조치 경로가 있어야 한다. 같은 사건에 Issue를 무제한 생성하지 않는다. 운영 기능을 제한할 때는 사용자에게 현재 상태를 명확히 보여 주고 검증되지 않은 결과를 accepted로 내보내지 않는다. 에이전트가 관측 이상만으로 운영 권한을 확대하거나 실결제·사용자 데이터를 조작하지 않는다.

첫 복구 훈련은 fixture/preview/모의 registry에서 장애 하나를 주입하는 방식으로 한다. 운영 장애를 새로 만들거나 실제 발행 보류를 풀지 않는다. 장애가 없었던 것을 가짜 성공 기록으로 남기지 않고, 훈련 증거와 실제 운영 사건을 구분한다.

**완료 기준:** 모의 장애 하나에서 영향 배포·조치 권한·복구 경로를 기존 문서와 증거로 찾을 수 있고, 복구가 확인된다. 지표 계산의 표본/분모 오류를 negative test가 검출한다.

## 13. 정기 유지보수·업무량 제한

### 13.1 초기 운영 주기

아래는 일정 자동 등록이 아니라 제안하는 운영 주기다. 실제 담당과 실행 환경을 정하기 전 외부 점검·알림을 자동 실행하지 않는다. 점검은 무조건 PR을 만드는 행사가 아니다.

| 주기 | 점검할 것 | 산출물·제한 |
|---|---|---|
| 작업 시작·Ready 전 | 범위·중복 작업·공유 자원·계약 영향·표적 테스트 | 기존 Issue/PR 내용 갱신. Ready PR 상한 유지 |
| 주 1회 | 일반 의존성, 기한 도래한 불안정 테스트, 외부 CLI 검증 필요성, 반복 실패 | 관련 업데이트는 소수로 묶고 외부 점검은 승인된 예산만 사용 |
| 최근 20개 PR 단위 | diff 예산·runner 시간·대기·재리뷰·후속 회귀·자주 함께 바뀌는 파일 | 다음 개선 경계 하나 선택. 작업 수를 성과로 삼지 않음 |
| 월 1회 | 임시 분기/문서 상태·오래된 미검증 백엔드·성능 추세·무효한 예외 | 기존 tracking Issue의 후속 순서 조정. 자동 삭제·대량 Issue 발행 금지 |
| 릴리스 전 | 공개 계약·지원 OS smoke·tarball·채널별 보류·부분 실패/rollback | 정확한 SHA·artifact·배포 상태 증거 |
| 보안/운영 사건 발생 시 | 영향·노출·승인된 완화·복구·최소 회귀 | 정기 일정을 기다리지 않되 같은 사건은 하나로 추적 |

### 13.2 예외와 유지보수 부채

크기 예외, 임시 격리, 기존 의존성 위반, 지원 유예는 이유·담당·재검토 조건을 남긴다. 기한 경과를 자동 허용으로 처리하지 않는다. 기존 위반 전체를 한 번에 제거하는 대신 새 위반을 막고, 근거가 있는 기존 문제를 작은 PR로 줄인다.

반복되는 유지보수 작업 때문에 핵심 제품 개발이 멈추면 우선순위와 자동화 비용을 오너가 재조정한다. 새 봇·문서·required gate의 개수를 성과 지표로 삼지 않는다. 검증 비용은 줄일 수 있지만 필수 계약·보안·의미 보존 경계를 조용히 낮추지 않는다.

## 14. 실행 순서·PR 단위·의존성

### 14.1 실행 원칙

tracking Issue 하나에 전체 순서를 두고 **다음 실행 가능한 작업만** Issue/PR로 만든다. 아래 행은 작업 단위이며 사전에 고정한 PR 개수가 아니다. 예산을 넘으면 독립적인 동작·검증·rollback 기준으로 분해한다. 구현과 그 회귀 테스트를 따로 떼지 않는다. 이미 충족한 항목은 현재 증거를 연결하고 중복 구현하지 않는다.

기존 계획 ID `P00~P13`은 유지한다. 커진 정책 작업 `P02`는 `P02a/P02b`, 릴리스 복구 `P12`는 `P12a/P12b`로 분리한다. 유지보수 작업은 `P14~P22`로 추가한다. `P06b/P08/P10/P13b/P17b/P19b`는 조건 충족 시 구현한다. 이들의 요구사항을 빼는 것이 아니라 불필요한 플랫폼 도입·외부 실행을 먼저 하지 않는다는 뜻이다.

### 14.2 첫 실행 묶음 — 다른 대규모 정비보다 우선

먼저 **P00 → P01·P03 → P02a·P02b**를 진행하고, **P07a / P14a / P15 / P16a** 중 준비된 작은 경계부터 착수한다. 화살표는 큰 흐름이며 아래 개별 의존성을 따른다. 서로 다른 파일·자원을 쓰는 작업만 병렬화하고 Ready PR은 작성자당 최대 2개를 초기값으로 둔다.

### 14.6 실행 에이전트에 넘기는 작업 계약

```text
1. 현재 dev SHA·상태·적용 AGENTS·대상 작업 ID를 확인한다.
2. 이미 구현된 부분, 실제 변경할 범위, 공개 계약 영향, 비목표를 기록한다.
3. 필요한 테스트와 수정 전 실패/현재 baseline을 확보한다.
4. 한 동작·계약 단위만 수정하고 해당 테스트·문서와 함께 검증한다.
5. 실행 명령·exit code·head/base/시험 트리·artifact·미실행 항목을 남긴다.
6. 계약/보안/의미 보존 검사 완화나 범위 밖 결함을 발견하면 멈추고 보고한다.
7. 발행 권한이 있으면 같은 범위의 기존 Issue/PR을 갱신한다.
   별도 권한 없이 새 과제를 대량 발행하거나 merge/배포하지 않는다.
```

검사기가 이미 있으면 확장한다. 현재 구현이 완료 기준을 충족하면 새 코드를 만드는 대신 증거를 연결한다. 하나의 이슈에서 모든 후속 작업을 한 번에 구현하는 에이전트 루프를 만들지 않는다.

## 15. 전체 수용 기준·효과 측정

### 15.1 모든 변경에 공통인 완료 조건

PR은 범위·공개 계약 영향·비목표·되돌리기를 설명하고, 해당 동작 테스트와 같은 작업 단위로 제출된다. 구현·테스트·문서에서 필수 안전장치를 약화하지 않는다. 실행 증거에는 다음 정보가 연결돼야 한다.

| 항목 | 필요한 정보 |
|---|---|
| 대상 | repository·PR/작업 ID·head SHA·base SHA·시험한 merge/tree/build 식별자 |
| 방법 | 검증 프로파일/정책 버전·명령·환경/도구 버전·기대값 |
| 결과 | 실제값/exit code·passed/failed/inconclusive/stale/canceled·누락 사유 |
| 증거 | 최소 로그·fixture·필요한 artifact hash/링크·민감정보 제거 |
| 판단 | 남은 위험·예외 승인·다음 조치·rollback·발행 채널/보류 상태 |

모든 PR에 장문 보고서를 요구하지 않는다. 이미 CI가 제공하는 값은 중복 손기록하지 않고 실행 ID와 신뢰 가능한 artifact로 연결한다. 증거가 현재 대상과 맞지 않으면 오래된 검증으로 merge-ready를 표시하지 않는다.

### 15.2 통합 완료 기준

| 영역 | 수용 기준 |
|---|---|
| 규칙·문서 | 개인 작업공간 없이 공용 규칙을 찾고 실제 에이전트에서 로딩됨. 현재/폐기/역사 문서의 구분 가능 |
| PR·Issue | 크기 예외가 명시되고 독립 검증/rollback 가능. dev 반영·배포 완료·취소가 구분됨 |
| 계약 | 대표 CLI/API/설정/설치 구버전 fixture가 정책대로 동작. 내부 구현 정리가 공개 계약을 몰래 바꾸지 않음 |
| 테스트 | 알려진 회귀와 제한된 negative fixture를 실제 검출. 기대값 갱신/재실행/격리로 실패를 숨기지 않음 |
| 병렬·자원 | 두 세션 실행 미혼합. 취소/timeout 뒤 소유 자원 정리와 다음 호출 성공 |
| CI·리뷰 | 필요한 job의 skipped/missing/canceled는 통과 아님. 낡은 head/base 결과 재사용 금지. 중복 리뷰가 구조적으로 억제됨 |
| 외부 의존성 | 실제 검증 버전과 미검증/인증/장애/호환성 실패 구분. 업데이트 대기열이 작업 상한을 따름 |
| 발행 | 검증 artifact와 발행 입력이 같음. partial success/integrity mismatch/old latest/rollback 처리 가능 |
| 유지보수 | 임시 코드의 담당/제거 조건, 기한 있는 테스트 격리, 근거 기반 hotspot 개선, 성능 추세와 사건 대응이 연결됨 |
| 안전 경계 | 의미 보존·결정론/모델 분리·원문/인증 비공개·취소된 연구·발행 보류 정책이 약화되지 않음 |

### 15.3 효과 측정과 강제 적용 조건

초기 최근 20개 PR을 기준선으로 삼고 후속 표본과 비교한다. 타입·위험·규모가 다른 PR을 무작정 같은 집단으로 비교하지 않는다. 첫 10개 PR의 크기 정책은 경고로 관찰하고 false alarm과 실제 검토 부담을 평가한다.

측정 항목은 reviewable/raw diff, 첫 피드백까지 시간, Ready→merge, CI 대기와 실행/runner-minutes, 같은 diff 리뷰 재요청, 무효화된 QA, merge 후 회귀/되돌리기, 불안정 테스트 빈도·격리 기간이다. 필요한 로그가 없으면 unknown으로 남긴다. 성공만 기록해 실패/취소/미실행이 지표에서 사라지지 않도록 한다.

경로별 CI, 비용이 큰 자동 QA, 성능 blocking gate는 측정 이득·안전한 분류·책임자를 확보한 뒤 도입한다. 그 전에는 기존 결정론 검사와 필요한 수동 검증을 유지한다. 비용 절감률이나 품질 향상 수치는 실측 전 약속하지 않는다.

**완료의 의미는 문서·봇·테스트 개수 증가가 아니라, 변경을 작게 검토하면서도 계약 위반·회귀·자원 누수·외부 호환성 문제·부분 발행을 확인하고 복구할 수 있는 상태다.**
